# 設計ログ — fc8weight

実装しながら下した判断と、その理由を残す。**採用した案だけでなく、捨てた案・死んだコードとその死因も記録する。**
コードを読めば「何がそうなっているか」は分かるが、「なぜそうしなかったか」はここにしか残らないため。

## 2026-07-27 — 必要筋力モデルの全面作り直し

### 変更前後

| | 旧モデル | 新モデル |
|---|---|---|
| 必要筋骨 | `素材密度 × サイズ係数 × 0.7` | 素材ティア表 ＋ サイズ階層 |
| 金の剣 | 10.1 | 20 |
| ダイヤの剣 | 1.7 | 50 |

新モデルの式: `必要筋骨 = 素材の剣基準値 + (サイズ値 − 軽の値) × 素材の倍率`

| 素材 | 剣基準値 | 倍率 | 軽（剣） | 中（太刀・斧） | 重（大剣・大槌） |
|---|---|---|---|---|---|
| 木・石・革 | 0 | — | 0 | 0 | 0 |
| 鉄・鋼・銅・銀 | 10 | ×1 | 10 | 12 | 16 |
| 金 | 20 | ×1 | 20 | 22 | 26 |
| ダイヤ・エメラルド | 50 | ×2 | 50 | 54 | 62 |
| ネザライト | 100 | ×3 | 100 | 106 | 118 |

### なぜ作り直したか

旧モデルは「現実の比重」を軸にしていた。金は密度24で最重、ダイヤは密度4で石と同じ軽さ。
物理的には正しい。だが**ゲームの進行度と真逆を向いていた。**

- 金の剣: 重さ14.4（全武器で最重）なのに、必要筋骨は20（安い）
- ダイヤの剣: 重さ2.4（羽のように軽い）なのに、必要筋骨は50（高い）

ツールチップにこの2つが並ぶと、プレイヤーには矛盾としか見えない。
**現実の比重とゲーム進行度は、そもそも両立しない2本の軸だった。**
どちらかを捨てるしかなく、ゲームである以上、進行度を残した。

### 捨てずに降格させた

密度モデルは削除していない。**未知のmod素材に対するフォールバック**に降格させた。

約270modのmodpackで実運用しているため、ティア表のキーワード（iron / diamond / netherite …）
に当たらない武器は必ず出る。そこで三段フォールバックにした。

1. **ティア表** — レジストリIDの素材キーワードで判定
2. **密度 × サイズ** — 旧モデル。`simplyswords:mithril_longsword` のような素直な命名を拾う
3. **攻撃力 × 係数** — 最も雑だが、必ず何らかの値を返す最後の砦

「未知の入力で例外を投げず、精度を段階的に落として必ず答えを返す」という方針を
モデル全体の構造として実装した形。

## バグ① 掘削道具が武器化した

### 発見の経緯

「必要筋骨 × 0.5 を攻撃力に加算する」機能を `ItemAttributeModifierEvent` で実装した直後、
別件で「他に問題はないか」を洗い直していて、自分が書いた発動条件を読み返して気づいた。

条件はこう書いてあった — **「既存の ATTACK_DAMAGE ADDITION が正なら加算する」。**
これは「武器かどうか」の判定のつもりだった。

### 何が起きていたか

バニラの `PickaxeItem` は attack_damage の ADDITION を持っている。
`DiggerItem` のコンストラクタが `attackDamage = 引数 + Tier.getAttackDamageBonus()` を
計算しており、鉄で3.0、ダイヤで4.0、ネザライトで5.0。
これが「正のADDITION」という条件を素通りしていた。

| アイテム | バグ時 | 修正後 |
|---|---|---|
| ダイヤのツルハシ | 必要筋骨50・攻撃力30 | 要求なし・攻撃力4 |
| 鉄のシャベル | 必要筋骨10・攻撃力8.5 | 要求なし・攻撃力3.5 |

**誰も持てない30ダメージのツルハシ**が出来上がっていた。
しかも必要筋骨50はダイヤの剣と同じ要求値で、掘削が完全に不可能になる。

### 最初に考えた修正が通らなかった

まず「既存ADDITIONが `minWeaponDamageToGate`(3.0) 以上のときだけ」に変えようとした。
このmodが他の箇所で使っている既存の武器判定しきい値なので、一貫性もある。

**が、鉄のツルハシはちょうど3.0、ダイヤは4.0。両方ともしきい値を通過する。**
数値のしきい値では道具と武器を分離できないと判断して、この案を捨てた。

### 採った解決

型で判定した。

```java
private static boolean isMiningTool(ItemStack stack) {
    Item item = stack.getItem();
    return item instanceof DiggerItem && !(item instanceof AxeItem);
}
```

2つの判断が入っている。

- **具象3クラス（Pickaxe / Shovel / Hoe）ではなく基底の `DiggerItem` を見た。**
  modded のパクセル・ドリル・削岩機も `DiggerItem` を継承しているので、
  こちらが何も知らないまま自動的に除外される。列挙は必ず漏れる
- **`AxeItem` だけ除外の対象外にした。** 斧は `DiggerItem` を継承しているが、
  バニラでもEpicFightでも正当な武器。型の継承関係とゲーム上の意味が一致していない箇所

### 重さだけ別の値を返すようにした

必要筋骨を返す `of()` は 0 を返すが、重さを返す `weightOf()` は **NaN** を返している。

0 と NaN を区別した理由: 呼び出し側が
**「これは本当に無重量の初期装備（木の剣）」**と**「素材が判定できなかった」**を
区別できるようにするため。NaN のときだけ密度モデルへフォールバックさせたい。

結果、ツルハシは筋力要求こそ無いが、物理的な嵩に応じた重さは残る。
「武器ではないが、重い物ではある」という状態を表現できた。

## バグ② 素材名を含むだけのアイテムが重量を持った

### 何が起きていたか

`minecraft:netherite_ingot` を手に持つだけで重量100、移動速度 -50%。
エメラルドで -25%、鉄インゴットとリード（動物を繋ぐ紐）で -5%。
**採掘・取引・動物の誘導という、最も日常的な操作すべてで再現する。**

### 原因は「javadocに書いてあった前提を、実装から落としたこと」

旧 `weaponWeight()` にはガードがあった。

```java
double dmg = weaponBaseDamage(stack);
if (dmg >= MIN_WEAPON_DAMAGE_TO_GATE) {   // ← これ
    double mat = MaterialWeight.weaponWeight(stack);
    ...
}
```

ティア表へ差し替えるとき、このガードを**消してしまった**。
新しい判定ロジックに気を取られて、その手前にあった前提条件を落とした形。

しかも、この前提は2箇所のjavadocに明記されていた。

- `WeightHandler.weaponWeight` — "material path is used only for actual weapons"
- `MaterialWeight.weaponWeight` — "Caller is responsible for the 'is this actually a weapon' check"

**呼び出し側の責務としてコメントに書かれていたが、コードでは強制されていなかった。**
コメントで表明した契約は、実装が変わった瞬間に黙って破られる。

### 教訓として残す

ティア表・密度モデル・攻撃力プロキシの三段フォールバックは、**すべてレジストリIDの文字列から素材を解決する**。
つまりどの段も「これは武器か」を判定できない。判定はフォールバックに入る前に一度だけ済ませる必要があった。
ガードを関数の先頭へ移し、三段すべての手前に置いた。

## バグ③ `"axe"` が `"pickaxe"` に部分一致していた

`"iron_pickaxe".indexOf("axe")` は真になる。`pick**axe**` の中に含まれるため。
結果、ツルハシがサイズ階層「中」（戦斧と同じ）と誤判定されていた。

キーワード部分一致でアイテムを分類する設計の、典型的な破綻。
`"gold"` は `golden_apple` に、`"lead"` は `leather` に、`"axe"` は `pickaxe` に当たる。

対処は、キーワード判定に入る前に `pickaxe` / `pick_axe` を先に弾く形にした。
**根本解決ではない。** 部分一致である限り同種の誤爆は再発しうる。
本来はアイテムタグ（`minecraft:swords` 等）で分類すべきだが、
約270modの環境ではタグを付けていないmodが多く、文字列判定を捨てられなかった。
「正しくないと分かっているが、代替がないので使い続けている」箇所として記録しておく。

## 公開前レビューで判明した、設計コメントが守れていない不変条件

移動速度ペナルティは6系統ある — 重さ・過重量武器・所持武器ティア・バックパック・防御力リニア・防具筋力ゲート。
**それぞれ個別に1.0未満へクランプしている**ので、コード上は「速度が0にならない」ことが保証されているつもりだった。

だが `MULTIPLY_TOTAL` は掛け算で合成される。6つ同時に最大値へ達すると:

```
0.01 × 0.70 × 0.60 × 0.10 × 0.01 × 0.20 ≒ 0.0000084
```

厳密には0ではないが、実用上は完全停止と同じ。
**「各修正子を個別にクランプすれば停止を防げる」という前提が、複合適用については成立していない。**

**単体の不変条件は、合成したときの不変条件を保証しない。**

### どう直したか — 修正子を6個から1個に減らした

per-modifier のクランプでは「積に対する上限」を表現できない。表現できる場所が存在しない。
そこで**6系統を先に合成してから、その結果に1つだけクランプを掛ける**形にした。

```java
double retained = (1 - weightSlow) * (1 - overMoveSlow) * (1 - heldSlow)
                * (1 - backpackSlow) * (1 - armorDefSlow) * (1 - armorStrGateSlow);
double combinedSlow = Math.min(totalMaxMoveSlow, 1.0 - retained);
```

各系統の個別上限は残してある（「筋力不足のペナルティは最大30%」といった意味を持つため）。
その上に、積に対する上限を1つ足した形。

副産物として `AttributeModifier` が6個から1個に減った。
攻撃速度のペナルティだけは別属性なので独立のまま残している。

**設計として言えること**: 不変条件は、それを表現できる粒度に置かないと守れない。
「各パーツが安全なら全体も安全」は、合成が乗算のときには成り立たない。

## 移動速度ペナルティの上限撤廃と、0.99 で止めた理由

### 撤廃した理由

上限は -40% だった。だが約270modの環境では移動速度を数百%積める手段が複数あり、
**-40% は誤差**でしかない。重装備のコストが実質無料になっていた。

### なぜ 1.0 ではなく 0.99 なのか

このペナルティは `MULTIPLY_TOTAL` 演算で適用している。
Minecraftの属性計算は、各 `MULTIPLY_TOTAL` について `値 *= (1 + 修正値)` を順に掛ける。

**修正値がちょうど -1.0 だと、値が 0 に固定される。**
そのあとどれだけ速度バフを掛けても `0 × 何か = 0` で、永久に動けなくなる。
救出手段が原理的に存在しない状態を作ってしまう。

1%だけ残しているのは復帰可能性を確保するため。実効的な差はほぼ無い。

### 「99%盛れば打ち消せるのでは」という疑問を検証した

打ち消せない。乗算なので、+99%のバフ（×1.99）を掛けても
`0.01 × 1.99 = 0.0199` で通常の2%にしかならない。

| 速度バフ | 重さ-99%適用後 | 通常比 |
|---|---|---|
| なし | 0.001 | 1% |
| +99%（×1.99） | 0.00199 | 2% |
| +500%（×6） | 0.006 | 6% |
| **+9900%（×100）** | 0.1 | **100%** |

等倍に戻すには ×100、つまり **+9900%** が必要。
`MULTIPLY_TOTAL` は比例ペナルティなので、プレイヤーがどれだけ速度を盛っても
その盛った速度に対して常に1%まで削る。**バフ積みで踏み倒せない性質**を利用している。

減算ペナルティ（`ADDITION`）にしていたら、バフを積むだけで無効化できていた。
**演算子の選択がそのままバランス設計になっている**例。

## 使われなくなったもの と、その死因

**削除していないものが多い。** 死因ごとに「復活しうるか」が違うため。

| 対象 | 死因 | 復活しうるか |
|---|---|---|
| `strRequirementFactor = 0.7` | **式そのものが消えた。** 「必要筋骨 = 重さ × 0.7」という計算が階層テーブルに置き換わり、係数を掛ける相手が存在しなくなった | **削除済み。** 設定しても黙って効かないキーを残すのは、検証を誤らせるだけなので消した |
| `freeWeight = 15.0` | **設計思想が変わった。** 「全員一律の無料枠」から「振った筋力に比例する枠」へ移行。`strAllowanceEnabled = true` の間は分岐の反対側に入るため到達しない | する。設定1つで生き返るので残している |
| `weaponWeightFactor = 1.0` | **段階的に降格。** 元は「重さ = 攻撃力 × 係数」という最初期の雑なモデルの係数。密度モデル導入で第2フォールバックへ、ティア表導入で第3フォールバックへ下がった | 現役。最後の砦としてまだ生きている |
| `WeightHandler.armorDefense()` | **呼び出し元が消えた。** 防具の重さを「防御力の合計」で近似していた頃の実装。素材×部位係数モデルに置き換わり、メソッド本体だけが残った | しない。純粋な死にコード |
| 密度テーブル（金24・ダイヤ4等） | **死んでいない。主役から降りた。** 現実の比重という軸が、ゲーム進行度の軸と両立しなかった | 現役。フォールバックとして機能中 |
| `gateExemptItems` の石ティア6件 | **不要になった。** 石は必要筋骨0なので、除外リストに入れる意味がなくなった | しない |

### この表から言えること

設定項目が使われなくなる理由には、少なくとも3種類ある。

1. **式が消えた** — 二度と戻らない。削除してよい
2. **分岐の反対側に入った** — 設定1つで生き返る。残すべき
3. **降格した** — まだ動いている。消してはいけない

**「使われていない = 消してよい」ではない。**
死因を調べずに一括削除すると、フォールバック経路を丸ごと壊す。

## 実機で裏を取る必要が残っている項目

コードからは判定できず、実際に動かさないと確認できないもの。**すべて未検証。**

1. **EpicFightのダメージ計算との二重計上**
   `WeightHandler.efDamageBonus()` はEFの武器capabilityが持つATTACK_DAMAGEを別途集計している。
   今回の攻撃力ボーナスは `ItemAttributeModifierEvent` 経由でアイテム側の修正子として入るため、
   EFが独自ルートで計算する場合に加算されるのか無視されるのか、静的には判定できない

2. **EF非対応の modded 武器で移動ペナルティが跳ねる**
   `heldWeaponSlow` はEFカテゴリで判定できないとき攻撃力しきい値へフォールバックする
   （11以上=重い→-40% / 7以上=中→-25%）。攻撃力ボーナスで膨らんだ値がこのしきい値を通るため、
   **EFが知らない武器だけ** -10% → -40% に跳ねる可能性がある。
   バニラの剣はEFが `SWORD` カテゴリを持つのでこの経路を通らない

3. **属性値の実測**
   `/attribute @s minecraft:generic.movement_speed get` で最終計算値を確認する。
   他modが移動速度を属性以外の経路（移動コードの直接書き換え）で制御していた場合、
   このペナルティ設計は前提から崩れる

## 未解決の設計課題

| 課題 | 内容 |
|---|---|
| 語彙の重複 | 武器の「重さ」と「必要筋骨」が完全に同一の数値になった。1つの数値に2つの名前が付いている状態で、説明時に必ず理由を問われる |
| 金 > 鉄 の逆転 | 金の剣(14)が鉄の剣(10)より強くなった。`MaterialWeight` のjavadocには "gold is the heaviest yet makes the worst weapons" と書かれており矛盾する。金は耐久が極端に低いので「高火力・すぐ壊れる」という筋は通せる |
| サイズ分類の不一致 | `nodachi` と `scythe` を新テーブルでは「重」に入れたが、密度モデルでは 0.7 / 0.8（中相当）。フォールバック経路でのみ現れる不整合 |
| 部分一致の罠 | `"axe"` は `waxed_copper_block` にも一致する。現状は攻撃力を持たないため実害ゼロだが、潜在的な地雷 |
| 防具が3経路で減速 | 重さ・防御力リニア・防具筋力ゲートが独立に `MULTIPLY_TOTAL` で合成される。鉄フル装備の新規キャラで `0.95 × 0.70 × 0.20 = 0.133`、通常の13%まで落ちる |
